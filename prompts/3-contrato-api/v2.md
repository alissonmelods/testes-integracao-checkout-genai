# Prompt 3: Contrato de API (v2)

| | |
|---|---|
| **Objetivo** | Gerar testes que garantam que o serviço de Pedidos respeita os contratos das APIs que ele consome |
| **Técnica** | Chain-of-thought (raciocínio em passos explícitos antes do código) + contrato como fonte única da verdade |
| **Anexos** | Contratos (`contratos/*.yaml`), regras (`docs/regras-de-integracao.md`), `IntegracaoBase.java`, todo o código de `src/main/java`, `application.yml` e `pom.xml` |
| **Resposta da LLM** | [experimentos/respostas/3-contrato-v2.md](../../experimentos/respostas/3-contrato-v2.md) |

## O que mudou em relação à v1 (e por quê)

| Ajuste | O que a v1 mostrou |
|--------|--------------------|
| Os testes leem `contratos/*.yaml` em tempo de execução, sem copiar schema nem regra para o código | A v1 transcreveu o contrato à mão em asserções (`ContratoRegras`) e avisou que, "se o YAML mudar, os testes precisam mudar junto". Teste de contrato que não lê o contrato deixa de pegar a mudança que mais importa |
| Validar também os stubs contra o schema de resposta | Nas outras suítes os stubs omitiam campos obrigatórios. Um stub fora do contrato faz o teste passar contra uma resposta que o provedor nunca envia |
| Passos explícitos: listar o que o Pedidos envia e lê, comparar com o YAML e só então gerar os testes | Os dois achados mais valiosos da v1 (token no PIX e total zero) apareceram quase por acaso. A tabela torna essa comparação sistemática e revisável |
| Pedir a compatibilidade entre os dois contratos | O achado do total zero era isso: um valor válido no Estoque (`precoCentavos: 0`) virava um valor inválido no Pagamentos (`valorCentavos` mínimo 1) |
| Estender `IntegracaoBase` nos testes que passam por POST /pedidos | Padronizar a infraestrutura com as outras suítes |

## Texto enviado

```text
Atue como um engenheiro de QA especialista em testes de contrato orientados pelo consumidor (consumer-driven
contract testing).

## Contexto
O serviço de Pedidos (Java 21, Spring Boot 3.5.16, JUnit 5, AssertJ e WireMock 3.13) consome duas APIs REST de
outros times: Estoque e Pagamentos. Os contratos OpenAPI 3.0 delas, as regras de integração, a classe base de
testes e o código do serviço estão anexados.

## Raciocine em passos e mostre cada passo antes do código
Passo 1. A partir dos clients (EstoqueClient, PagamentosClient) e dos tipos ContratoEstoque e ContratoPagamentos,
liste tudo o que o Pedidos ENVIA a cada API (método, caminho, headers, campos do corpo e seus tipos) e tudo o que ele
LÊ das respostas (status HTTP tratados e campos usados).
Passo 2. Compare cada item com o contrato (obrigatoriedade, tipo, formato, enum, mínimo/máximo, nullable) e
classifique: compatível, divergente ou não coberto pelo contrato. Inclua a compatibilidade entre os dois contratos
quando um valor de um vira entrada do outro (por exemplo, o preço do Estoque compõe o valor cobrado no Pagamentos).
Passo 3. Só então gere os testes, cobrindo os itens da tabela.

## Regras para os testes
- O YAML é a fonte da verdade. Os testes devem ler contratos/estoque-api.yaml e contratos/pagamentos-api.yaml em
  tempo de execução. Não copie schemas, enums nem limites para o código do teste: se o contrato mudar, o teste tem
  que quebrar sozinho.
- Valide o corpo de cada requisição que o Pedidos envia contra o schema do contrato, usando matchingJsonSchema do
  WireMock (converta o schema OpenAPI 3.0 em JSON Schema, resolvendo $ref e nullable), e valide os headers
  obrigatórios a partir dos parâmetros do contrato (ex.: Idempotency-Key com minLength e maxLength).
- Use os exemplos do próprio YAML como respostas dos stubs e valide que toda resposta de stub usada obedece ao schema
  de resposta do contrato.
- Cubra o lado da leitura: cada status documentado das operações que o Pedidos usa é tratado como as regras mandam,
  e campos extras na resposta são ignorados.
- Sem dependências novas: só JUnit 5, AssertJ, Spring Boot Test, SnakeYAML (já vem com o Spring Boot), Jackson e
  WireMock 3.13.
- Testes que passam por POST /pedidos estendem IntegracaoBase (anexada) e usam postarPedido(json). Testes só dos
  clients podem injetar EstoqueClient e PagamentosClient do contexto, também estendendo IntegracaoBase. Não crie
  WireMock nem contexto próprio e não use Mockito.

## Formato da resposta
1. Tabela do Passo 1 e tabela do Passo 2.
2. O código, no pacote com.estudo.checkout.contrato: uma classe que carrega um contrato e devolve o JSON Schema de
   um componente ou as restrições de um parâmetro, e as classes de teste.
3. As divergências encontradas, com o teste que as demonstra.

[anexos]
```

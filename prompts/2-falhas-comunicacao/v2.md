# Prompt 2: Falhas de comunicação e casos de erro (v2)

| | |
|---|---|
| **Objetivo** | Gerar casos de falha na comunicação entre Pedidos, Estoque e Pagamentos |
| **Técnica** | Few-shot (um teste de exemplo no estilo esperado) + checklist de tipos de falha + regras como fonte da verdade |
| **Anexos** | Contratos (`contratos/*.yaml`), regras (`docs/regras-de-integracao.md`), `IntegracaoBase.java`, todo o código de `src/main/java`, `application.yml` e `pom.xml` |
| **Resposta da LLM** | [experimentos/respostas/2-falhas-v2.md](../../experimentos/respostas/2-falhas-v2.md) |

## O que mudou em relação à v1 (e por quê)

| Ajuste | O que a v1 mostrou |
|--------|--------------------|
| Regras e contratos anexados, com a instrução de **testar pela regra e apontar divergências** em vez de adaptar o teste ao código | A própria resposta avisou que "as expectativas saem do código e dos Javadocs", porque os contratos não vieram. Teste derivado do código confirma o código, inclusive os bugs |
| Infraestrutura fixa: estender `IntegracaoBase`, sem WireMock, `@RegisterExtension`, `@DynamicPropertySource` ou `@Nested` próprios | O `WireMockExtension` com `@Nested` reiniciava os servidores em outra porta e o contexto do Spring ficava apontando para a porta antiga: 48 de 63 testes falharam e alguns passaram pelo motivo errado |
| Timeout de 400 ms e atraso de `TIMEOUT_MS * 2`, sem `Thread.sleep` | Timeout de 1 s com atraso de 2,5 s deixou a suíte com ~14 s, quase tudo esperando |
| Do `motivo`, comparar só o prefixo do serviço | Asserções com o texto inteiro (`"pagamentos: indisponível após 3 tentativas"`) quebram com qualquer ajuste de mensagem |
| Stubs com os campos obrigatórios do contrato | Os stubs devolviam `{"id":"PAG-1","status":"APROVADO"}`, que o provedor real nunca envia (faltam `pedidoId`, `valorCentavos` e `metodo`) |
| Item 7 do checklist: resposta perdida e repetição idempotente (200) | Sem o contrato, a v1 não testou a repetição que devolve 200 com o pagamento original |
| Um teste de exemplo (few-shot) | Fixar o estilo: Arrange/Act/Assert, verificação das chamadas nos dois serviços e `@DisplayName` com ID e regra |

## Texto enviado

```text
Atue como um engenheiro de QA especialista em testes de integração e resiliência de APIs REST.

## Contexto
O serviço de Pedidos (Java 21, Spring Boot 3.5.16, JUnit 5, AssertJ e WireMock 3.13) faz o checkout em
POST /pedidos chamando via HTTP a API de Estoque (preço, reserva, confirmação e liberação) e a API de Pagamentos
(cobrança). As duas APIs são de outros times. Os contratos OpenAPI e as regras de integração estão anexados.

## As regras são a fonte da verdade
Escreva cada expectativa a partir das regras (R1 a R12) e dos contratos, não do código. Se o código anexado
contradisser uma regra, não adapte o teste ao código: escreva o teste pela regra e aponte a divergência no fim.

## Infraestrutura (use exatamente esta)
- Toda classe de teste estende IntegracaoBase (anexada). Ela sobe o serviço de verdade em porta aleatória e dois
  WireMockServer estáticos, ESTOQUE e PAGAMENTOS, que não reiniciam entre as classes. Não crie WireMock,
  @RegisterExtension, @DynamicPropertySource nem contexto próprio, e não use @Nested.
- Chame o serviço por HTTP com postarPedido(json) e consultarPedido(id). Não use Mockito nem @MockitoBean.
- O timeout dos clients nos testes é TIMEOUT_MS (400 ms). Para simular lentidão use withFixedDelay(TIMEOUT_MS * 2).
  Não use Thread.sleep.
- Os stubs devem responder como o provedor real: use os exemplos e os campos obrigatórios dos contratos.

## Exemplo do estilo esperado
package com.estudo.checkout.falhas;

import com.estudo.checkout.suporte.IntegracaoBase;
import com.fasterxml.jackson.databind.JsonNode;
import com.github.tomakehurst.wiremock.stubbing.Scenario;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.http.ResponseEntity;

import static com.github.tomakehurst.wiremock.client.WireMock.*;
import static org.assertj.core.api.Assertions.assertThat;

class FalhasComunicacaoIT extends IntegracaoBase {

    private static final String PEDIDO_PIX = """
            {"clienteId":"cli-1","itens":[{"sku":"LIV-001","quantidade":2}],"metodoPagamento":"PIX"}""";

    @Test
    @DisplayName("F01 [R6, R7] Pagamentos responde 503 e depois aprova: repete com a mesma Idempotency-Key e confirma")
    void pagamentoInstavelQueSeRecupera() {
        // Arrange: Estoque saudável e Pagamentos com 503 na 1ª tentativa e aprovação na 2ª
        ESTOQUE.stubFor(get("/produtos/LIV-001").willReturn(okJson("""
                {"sku":"LIV-001","nome":"Livro Testes de Software","precoCentavos":8990,"disponivel":10}""")));
        ESTOQUE.stubFor(post("/reservas").willReturn(jsonResponse("""
                {"id":"res-1","pedidoId":"p-1","status":"RESERVADA","itens":[{"sku":"LIV-001","quantidade":2}]}""", 201)));
        ESTOQUE.stubFor(post("/reservas/res-1/confirmacao").willReturn(okJson("""
                {"id":"res-1","pedidoId":"p-1","status":"CONFIRMADA","itens":[{"sku":"LIV-001","quantidade":2}]}""")));
        PAGAMENTOS.stubFor(post("/pagamentos").inScenario("instavel").whenScenarioStateIs(Scenario.STARTED)
                .willReturn(jsonResponse("""
                        {"codigo":"INDISPONIVEL","mensagem":"Serviço temporariamente indisponível"}""", 503))
                .willSetStateTo("recuperado"));
        PAGAMENTOS.stubFor(post("/pagamentos").inScenario("instavel").whenScenarioStateIs("recuperado")
                .willReturn(jsonResponse("""
                        {"id":"pag-1","pedidoId":"p-1","valorCentavos":17980,"metodo":"PIX","status":"APROVADO","motivo":null}""", 201)));

        // Act
        ResponseEntity<JsonNode> resposta = postarPedido(PEDIDO_PIX);

        // Assert: resultado para o cliente e o que foi (e o que não foi) chamado nos serviços externos
        assertThat(resposta.getStatusCode().value()).isEqualTo(201);
        assertThat(resposta.getBody().get("status").asText()).isEqualTo("CONFIRMADO");
        String chave = "pedido-" + resposta.getBody().get("id").asText();
        PAGAMENTOS.verify(2, postRequestedFor(urlEqualTo("/pagamentos")).withHeader("Idempotency-Key", equalTo(chave)));
        ESTOQUE.verify(1, postRequestedFor(urlEqualTo("/reservas/res-1/confirmacao")));
        ESTOQUE.verify(0, deleteRequestedFor(urlEqualTo("/reservas/res-1")));
    }
}

## Tipos de falha a considerar em cada chamada
Para GET /produtos/{sku}, POST /reservas, POST /pagamentos, POST /reservas/{id}/confirmacao e
DELETE /reservas/{id}:
1. resposta mais lenta que o timeout;
2. conexão resetada ou resposta vazia (Fault.CONNECTION_RESET_BY_PEER, Fault.EMPTY_RESPONSE);
3. HTTP 5xx;
4. HTTP 4xx inesperado;
5. resposta 2xx fora do contrato (campo obrigatório ausente, tipo errado, valor fora do enum);
6. falha transitória seguida de sucesso (cenários do WireMock);
7. resposta perdida: a tentativa foi processada pelo Pagamentos mas a resposta não chegou, e a nova tentativa
   recebe 200 com o pagamento original (repetição idempotente do contrato).
Nem toda combinação vale um teste: escolha as que exercitam regras diferentes e diga quais ficaram de fora e por quê.

## Em cada teste, verifique
- o status HTTP e os campos status e motivo (do motivo, só o prefixo "estoque:" ou "pagamentos:", nunca o texto
  inteiro);
- as chamadas feitas a ESTOQUE e PAGAMENTOS (verify com quantidade, e Idempotency-Key quando houver retentativa);
- o que não pode ter sido chamado (cobrança sem reserva, confirmação depois de falha, liberação depois de
  confirmação);
- o pedido gravado, com consultarPedido(id), quando fizer sentido.

## Formato da resposta
1. Tabela de casos: ID, regra(s), falha injetada (onde e como), resultado esperado e interações verificadas.
2. Uma classe FalhasComunicacaoIT (pacote com.estudo.checkout.falhas) estendendo IntegracaoBase, com o exemplo
   acima incluído e um @DisplayName com ID e regra em cada teste.
3. Divergências entre o código e as regras, se houver.

[anexos]
```
